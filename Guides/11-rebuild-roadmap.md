# 重建顺序与验收标准

状态：长期实施路线。创建于 2026-09-30，2026-10-25 更新当前状态；下方里程碑是完整目标，不代表全部已完成。

## 1. 已决定的范围

**Wonder Minecraft Launcher（奇想我的世界启动器）**以桌面式工作区为主交互，组件自由组合，插件严密且可持续扩展，本体轻量，最终单应用分发。新工程使用 `Wonder.*`，不恢复旧代码、不迁移旧数据、不兼容旧插件。

[产品目标](12-product-goals.md)规定交互与交付边界，[新架构](10-wonder-architecture.md)规定工程职责。六个工程是源码分层，不是六个需要用户分别安装的程序。

## 2. 里程碑

| 阶段 | 实施内容 | 完成证据 | 依赖 |
|---|---|---|---|
| M0 工程与关键可行性 | 六工程和依赖方向；新配置/日志目录；桌面与 worker 入口分流；单 EXE 初次发布；代码插件的平台沙箱实验与性能基准 | Release 构建；仅复制 EXE 可开窗；worker 不初始化桌面；角色/会话拒绝测试；对沙箱支持与限制有实验结论；测量体积/进程树/启动并锁定回归预算 | 采用方案 |
| M1 桌面与组件基础 | 工作区、组件库、任务栏、内部窗口；统一定义/实例/状态/动作；拖动、缩放、锁定、层级、保存；基础主题 | 内置交互组件可自由组合；多实例配置独立；输入不触发误拖动；窗口切换/最小化/恢复可用；空桌面重启仍为空；DPI/缩窗后可找回组件 | M0 |
| M2 最小完整扩展链 | 独立 SDK、贡献注册、manifest/依赖检查、包安装、按需激活、宿主代理、故障占位、禁用/卸载；声明包与独立代码示例 | 示例只引用 SDK；不改本体安装新组件；按钮、输入、动态状态、内部窗口和任务真正可用；越权/无效 UI/超时/崩溃局部失败；代码示例仅在已验证受限环境或标明实际权限的开发模式运行 | M1；安全模型依据 M0 结论 |
| M3 原版游戏闭环 | 版本解析、Java 探测、安装/修复、全新认证、不可变启动计划与进程管理；全部接入桌面组件和工具窗口 | 新账号登录、安装选定原版并进入游戏；任务切页/关窗继续；失败可诊断；真实退出码与脱敏日志；无旧数据读取 | M1；可与 M2/M4 的独立部分并行 |
| M4 插件正式开放门槛 | 平台沙箱、权限撤销、会话更新、依赖/冲突、来源验证、原子更新/回滚、资源预算、SDK 兼容测试 | 受限代码无法绕过文件/网络范围；死循环/洪泛/取消不响应有终止证据；未知能力/循环依赖/重复 ID 激活前拒绝；更新失败保持完整可用版本；发现顺序不影响启动贡献结果 | M2；与 M3 并行 |
| M5 首版交付 | 默认桌面、空状态/错误引导、可访问性、发布资源精简、单应用回归与文档 | 干净机器仅复制 EXE 即可打开完整默认桌面，安装插件并启停 worker，通过组件完成登录/安装/启动；总体性能满足 M0 锁定预算；开放能力均有验证 | M3 + M4；未通过沙箱的平台不开放受限代码通道 |
| M6 扩展生态 | 加载器、内容源、整合包、更多组件/主题/工作区能力，按独立适配器扩充 | 各扩展有独立样例、契约与真实使用验收；安装未激活插件不会导致常驻 worker 增长；对本体新增成本可解释 | M5，按新需求排序 |

M0 是工程与关键约束的可行性证明；M1 证明桌面交互；M2 证明可独立扩展；M3 证明游戏可用。首版同时需要桌面、扩展、游戏和分发链路，不能只凭一种能力宣布目标完成。

M4 的安全门槛不得用普通子进程、`AssemblyLoadContext`、取消令牌或权限清单替代。平台沙箱尚未达标时，明确限制该平台发布能力；不能把具有完整用户权限的代码运行宣传为受限模式。

## 3. 测试重点

| 范围 | 必须覆盖的行为 |
|---|---|
| 工作区 | 拖动/缩放与控件点击分离；位置/层级/锁定；多实例；空布局；DPI/缩窗找回；键盘移动与窗口焦点 |
| 生命周期 | 关闭视图不取消下载/游戏；隐藏暂停刷新；禁用/更新撤销订阅；插件缺失时保留占位；退出有界 |
| 组件协议 | 深度/节点/资源/更新频率有界；无效更新保留有效快照；重复 ID/未知动作拒绝；插件无法覆盖宿主提示 |
| 插件兼容 | 仅引用 SDK 的外部样例；清单、IPC、UI 协议和 SDK 分别检查版本；依赖环、缺失服务与版本冲突可诊断 |
| 权限与隔离 | 身份不由消息自报决定；拒绝未授权能力；文件路径/网络范围越界；撤销生效；未授权启动 worker 拒绝；平台沙箱实际验证 |
| 纯规则 | 版本继承与循环、平台规则、参数顺序、Classpath 冲突、路径非法字符、同级贡献稳定排序 |
| 数据快照 | 修改输入集合不改变已冻结计划；大小写策略一致；敏感参数不传给普通扩展；更新插件不改变在途计划 |
| 安装与包管理 | 校验失败、取消、中断恢复、暂存提交；归档越界/超限拒绝；来源身份变化不继承授权；失败回滚 |
| 进程与账号 | 中文/空格路径；输出流不阻塞；刷新失败与重新登录；凭据不进日志；真实登录与游戏退出 |
| 性能与发布 | 主进程和全部 worker 总成本；大量未激活插件；隐藏/移除后资源回收；只复制 EXE 的干净环境验证 |

单元测试验证确定性规则，集成测试验证磁盘/网络/进程/协议边界，桌面与真实账号/游戏单独验收。正式数据与凭据不写入测试夹具。发布验收必须使用实际单文件产物，不能以 IDE 中运行成功替代。

## 4. 原始实施顺序

先做 M0，并实现支撑 M1 的最小桌面画布与一个可交互内置组件。同步建立 SDK 的定义、实例和动作边界，尽早用独立示例验证，避免先做固定页面再推翻交互结构。

单应用发布、同文件 worker 模式、平台隔离和按需激活都属于会影响整体架构的约束，需要早做小范围验证。复杂生态能力分批实现，本体不预装整个插件集合。

微软应用注册参数与实际登录测试在 M3 准备，不阻塞桌面、契约或发布实验。原版服务可以与扩展工程并行开发，但最后统一由桌面组件调用，不能形成第二套互相独立的产品界面。
